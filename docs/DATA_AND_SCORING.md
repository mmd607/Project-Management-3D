# Data Model & Project Health Score

This document is the source of truth for what each displayed field means, where it comes
from, and — for the Health Score specifically — exactly how it's calculated. If the UI and
this document ever disagree, treat that as a bug to fix, not a documentation nit.

## Provenance categories

Every fact surfaced anywhere in the app carries one of these (`04-data/PROVENANCE_AND_CONFIDENCE.md`
in the Phase 0 pack is the original source):

| Category | Meaning |
|---|---|
| `DETERMINISTIC` | Directly read from a file/manifest/filesystem check. Not inferred. |
| `INFERRED` | Derived by a fixed rule from deterministic evidence (e.g. category classification). |
| `AI_INFERRED` | Generated by a language model from evidence context. Never treated as fact. |
| `UNKNOWN` | Insufficient evidence to say anything. |

The UI never blurs these — a value's badge always tells you which one it is.

## Entities

- **Workspace** — one local root folder the user opened. `rootPath`, `displayName`, `lastScanAt`.
- **Project** — one discovered project inside a workspace. `discoveryConfidence` is
  `DETERMINISTIC` (strong signal: `.git`, a recognized manifest, or a build/config file) or
  `INFERRED` (README-only, low confidence, never silently promoted or dropped).
- **ScanResult** — one scan run for one project: `status` (`OK`/`PARTIAL`/`FAILED`),
  `fileCount`, `directoryCount`, `totalSizeBytes`, `truncated`, `errors` (JSON array of
  `{path, message}`).
- **Evidence** — one atomic fact: `evidenceType`, `sourcePath`, `key`, `value`, `confidence`.
  Every "component", "lockfile", "framework", "language", "readme", "gitBranch" fact is one
  of these rows. Nothing is displayed that isn't backed by one.
- **IntelligenceProfile** — the rule-based (not AI) summary derived from Evidence:
  `description`, `category`, `projectType`, `architectureSummary`, `healthSummary`.
- **Technology** — one detected language/framework/package-manager/ecosystem, with its
  evidence source.
- **Recommendation** — a bounded, rule-triggered suggestion (e.g. "no README found"), never
  generic filler.
- **AiInsight** — one AI-generated explanation. Always `AI_INFERRED`. Stores which provider
  produced it and a hash of the input context (never the raw content, for privacy/debugging).

## "Scanned size" — what it does and doesn't mean

`totalSizeBytes` on a `ScanResult` is the sum of on-disk sizes of files actually visited
during that scan. It explicitly **excludes**:
- anything under a default-excluded directory name (`node_modules`, `.git`, `venv`, `dist`,
  `build`, caches, etc. — see `06-scanner/EXCLUSIONS.md` in the Phase 0 pack for the full list,
  user-editable, never hard-coded as a permanent limit);
- anything beyond the traversal safety cap (`truncated: true` on the scan result if hit).

This means "scanned size" can be smaller than the project's true on-disk size by design —
the UI's "excludes build/dependency folders" note next to the size figure exists specifically
so this isn't misread as "the whole project is only N MB."

## Components detected

A project's evidence can include a `component` key with one of these values, each backed by
a specific, literal check (never inferred from naming conventions or guesses):

| Component | Detected by |
|---|---|
| `tests` | A directory named `test`/`tests`/`__tests__`/`spec`/`specs`, **or** a test-framework dependency (jest/vitest/mocha/jasmine/ava/tape/pytest/unittest/rspec/phpunit) found in a manifest. |
| `docs` | A directory named `docs`/`doc`/`documentation`. |
| `deployment` | A `Dockerfile`, `docker-compose.yml`/`.yaml`, `Procfile`, or a `.github`/`.gitlab`/`.circleci` CI-config directory. |

A `lockfile` evidence entry (key `lockfile`) records the exact lockfile filename found
(`package-lock.json`, `yarn.lock`, `poetry.lock`, `Cargo.lock`, etc.).

## Project Health Score (`v1`)

**Explicitly not** the reference image's "82% Good" style badge — that number has no defined
meaning and this project doesn't reproduce it. This is a named, versioned, weighted,
per-component-explainable score computed only from real local evidence already described
above. Source: `apps/server/src/intelligence/healthScore.ts` (also the single place to change
if the formula ever needs to change — keep this doc in sync with it).

### Components and weights

| Component | Weight | Computable when | Scoring |
|---|---|---|---|
| Tests | 30 | Scan succeeded (any status but `FAILED`) | 100 if a `tests` component was found, else 0 — absence is real information here, not "unknown". |
| Documentation | 20 | Scan succeeded | 100 if README **and** a docs directory; 70 if README only; 0 if neither. |
| Dependencies | 20 | A package manager was detected at all | 100 with a lockfile; 50 with a manifest but no lockfile; 20 if multiple conflicting package managers were found with no lockfile pinning them. **N/A** (not 0) if no package manager evidence exists — the component doesn't apply to that project. |
| Structure & scan health | 20 | Scan succeeded | 100 if the scan completed with zero errors and wasn't truncated; 60 with unreadable paths; 40 if truncated. |
| Documented activity | 10 | Scan succeeded | 100 if a Git repository was detected, else 0. (No commit-history/frequency analysis exists yet — see Limitations.) |

If the scan itself failed (`status: FAILED`), **every** component is N/A and the overall
score is N/A — there's no evidence to judge anything from.

### Overall score

The weighted average over only the **computable** (non-N/A) components, renormalized to
their own weight sum — never treating an N/A component as a zero. The UI also shows
`coverage`: what fraction of the total possible weight was actually computable, so a 100/100
on a project with only 60% coverage still reads honestly as "confident about 60% of the
picture," not as a full, verified 100.

### What this deliberately does not do

- No network calls (no dependency-freshness/CVE lookups against a registry) — this is a
  local-first tool; "dependencies" is scored only on local reproducibility signals.
- No commit-frequency/recency "activity" scoring — that needs the Continuity/history feature
  (deferred, not built in v0); "activity" here only means "is this under version control."
- No code-quality/complexity static analysis — "Tests" only checks for the *presence* of a
  test setup, not whether the tests are good or passing (no code execution happens anywhere
  in this scanner, by design — see `08-security/SECURITY.md`).

## Known limitations (honest, not hidden)

- Inter-project **relationships** (e.g. "project A depends on local project B") are not yet
  detected — the graph's connections represent workspace membership only, never a claimed
  semantic relationship. Real evidence-based relationship detection (local path dependencies,
  workspace/monorepo links) is a reasonable next step, not yet implemented.
- The Health Score formula's exact weights (30/20/20/20/10) are a starting point, not
  empirically validated against real user judgment yet — they are adjustable in one place
  (`HEALTH_COMPONENT_WEIGHTS`) and versioned (`HEALTH_SCORE_VERSION`) specifically so they can
  be revised with evidence later without breaking anything silently.
